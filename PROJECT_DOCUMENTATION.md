# CloudGuardian AI

## 1. Project Overview

CloudGuardian AI is a FastAPI-based incident analysis prototype for cloud and Kubernetes operations. It exposes a small HTTP API and a browser console where an operator submits an incident question, selects an analysis workflow, and receives either a deterministic diagnostic response or a response generated by a Google ADK agent workflow.

The project is currently a proof of concept. Its observability, Kubernetes, and security integrations return fixed mock data rather than querying live systems. It now includes a guarded in-memory incident/action control plane for local demonstrations, but it is not yet a durable production control plane.

## 2. Problem Statement

Cloud incidents can require operators to correlate logs, infrastructure metrics, Kubernetes health, security indicators, root-cause hypotheses, and remediation actions. CloudGuardian AI is intended to bring those activities into one incident-response workflow so that an operator can submit a service problem and receive a consolidated analysis and recommended next steps.

The current repository demonstrates that workflow shape, but it does not yet connect the analysis to real production telemetry or execute remediation actions.

## 3. Project Objectives

- Provide a browser-based console for submitting incident-analysis requests.
- Expose an HTTP API for incident and remediation workflows.
- Correlate log, infrastructure, Kubernetes, and security signals.
- Use Google ADK agents and Vertex AI/Gemini for multi-stage incident reasoning when configured.
- Offer a fast deterministic mode for local or low-latency demonstrations.
- Produce root-cause, remediation, and incident-report outputs.
- Establish a deployable container and Cloud Build configuration for Google Cloud.

## 4. Technology Stack

### Application and API

- **Python**: The implementation language.
- **FastAPI**: Defines the web application and the `/`, `/ui`, and `/analyze` routes in `app/main.py`.
- **Pydantic**: Defines and validates the `AnalyzeRequest` request model through FastAPI.
- **Uvicorn**: Runs the ASGI application locally and in the Docker container.
- **python-dotenv**: Loads values from `.env` in `app/main.py` and `app/config/vertex_config.py`.
- **pytest**: Runs the focused control-plane tests in `tests/`.
- **Optional AI dependencies**: `app/requirements-ai.txt` adds Google ADK and Google Cloud packages for live model workflows. The default requirements intentionally support the local fast mode without that dependency graph.

### AI and workflow orchestration

- **Google ADK**: Supplies `Agent`, `ParallelAgent`, `SequentialAgent`, `LoopAgent`, `Runner`, and in-memory sessions.
- **Gemini 2.5 Flash**: The model named by all ADK agents in the workflow definitions.
- **Vertex AI**: `app/config/vertex_config.py` contains `vertexai.init` configuration using Google Cloud environment variables. That module is not imported by the application entry point, so initialization is not guaranteed during normal startup.
- **Google GenAI types**: `Content` and `Part` are used to construct the user message passed to the ADK runner.

### Cloud and infrastructure dependencies

`app/requirements.txt` declares packages for Google Cloud Logging, Cloud Monitoring, Firestore, Kubernetes, `requests`, and Google Generative AI. The current application source does not instantiate clients for those live services; the corresponding project tools return mock values.

### Frontend

- A single static HTML page at `app/ui/index.html`.
- Plain HTML, CSS, and browser JavaScript; no frontend framework or package manager is present.
- Google Fonts are loaded remotely: Manrope and JetBrains Mono.
- The page uses `fetch` with JSON and a 60-second `AbortController` timeout.

### Build and deployment

- **Docker**: `Dockerfile` uses `python:3.11-slim`, installs `app/requirements.txt`, and starts Uvicorn on port 8080.
- **Google Cloud Build**: `cloudbuild.yaml` builds and publishes `gcr.io/$PROJECT_ID/cloudguardian-ai`.
- **Cloud Run**: The README documents a source-based `gcloud run deploy` command.

## 5. System Architecture

The application has four main layers:

1. **Browser UI**: `app/ui/index.html` collects request fields and posts JSON to `/analyze`.
2. **FastAPI API**: `app/main.py` validates the request, selects `incident_workflow` or `remediation_loop`, and delegates execution to `run_agent`.
3. **Execution and workflow layer**: `app/services/runner_service.py` chooses fast mock analysis, a simple local text generator, or the Google ADK runner. ADK workflows compose specialized agents.
4. **Control-plane layer**: `app/services/incident_service.py` stores local incident and action state, while `app/services/action_executor.py` applies the allowlist, approval gate, and simulation-safe execution boundary.
5. **Tool and service layer**: `app/tools/` and `app/services/` provide logs, metrics, Kubernetes, and security data. These implementations are deterministic mocks in the current repository.

### Incident workflow

The ADK incident workflow is a `SequentialAgent`:

1. `parallel_analysis` runs `log_agent`, `infra_agent`, and `security_agent` concurrently.
2. `rootcause_agent` receives their outputs through ADK output keys and identifies a primary cause, contributing factors, severity, and estimated resolution time.
3. `recommendation_agent` produces immediate, short-term, and long-term remediation guidance.
4. `report_agent` creates an enterprise incident report.

### Remediation workflow

`remediation_loop` is a `LoopAgent` containing `recommendation_loop_agent` and `report_loop_agent`, with a maximum of three iterations. It suggests improved remediation and reports progress, but it does not call an executor, mutate infrastructure, verify fixes, or use the available `exit_loop` tool.

### Execution selection

`run_agent` applies the following precedence:

1. `fast_mode=True`: calls deterministic tool/service functions and returns a dictionary.
2. `fast_mode=False` and `use_simple_model=True`: composes deterministic text locally without an external model.
3. Both flags otherwise: creates an in-memory ADK session and runs the selected ADK workflow.

Because `fast_mode` defaults to `true`, the browser's default request does not execute the ADK workflow.

## 7. Features Implemented

### FastAPI service and health response

- **What it does**: Starts a FastAPI application named CloudGuardian AI and reports available workflows.
- **Files**: `app/main.py`.
- **How it works**: `GET /` returns status text, version `1.0.0`, and the workflow names `incident` and `remediation`.

### Browser operator console

- **What it does**: Provides fields for user ID, service name, workflow, fast mode, simple output, local-model mode, and an incident query.
- **Files**: `app/ui/index.html`, served by `GET /ui`.
- **How it works**: The responsive operations console loads incidents and pending actions, submits analysis requests, presents signal summaries and action plans, and lets an operator approve or reject pending actions.
- **Current boundary**: The navigation is visual, state is in memory, and the page uses polling-on-action rather than a real-time event stream.

### Analyze API

- **What it does**: Dispatches a validated request to one of two workflows.
- **Files**: `app/main.py`, `app/services/runner_service.py`.
- **How it works**: The API accepts `user_id`, `workflow`, `message`, optional `service_name`, `fast_mode` defaulting to `true`, and `use_simple_model` defaulting to `false`. Invalid workflow names receive HTTP 400. Dictionary results are spread into the success response; string results are returned under `response`.

### Deterministic fast analysis

- **What it does**: Returns a quick incident summary without a model call.
- **Files**: `app/services/runner_service.py`, `app/services/logging_service.py`, `app/services/monitoring_service.py`, `app/tools/kubernetes_tool.py`, and `app/tools/security_scan_tool.py`.
- **How it works**: It gathers fixed logs, fixed metrics, fixed security results, and fixed Kubernetes status, then reports an OOM/infrastructure-saturation hypothesis and three recommended next steps.
- **Action output**: It also emits a structured plan containing a low-risk restart proposal and a medium-risk memory increase proposal. These are routed through the control plane and require approval unless automation is explicitly enabled.

### Guarded incident and action control plane

- **What it does**: Creates an incident record for each dictionary analysis result and tracks proposed actions through pending, executed, rejected, or blocked states.
- **Files**: `app/services/incident_service.py`, `app/services/action_executor.py`, and `app/main.py`.
- **How it works**: The default configuration keeps automatic execution disabled. Pending actions can be reviewed in the UI or through the approval endpoints. The current restart executor records a simulation result; it does not call Cloud Run or Kubernetes.

### Local text generator

- **What it does**: Produces a short deterministic text response without an external LLM.
- **Files**: `app/services/runner_service.py` and the same mock tool/service modules.
- **How it works**: It is reachable only when `fast_mode` is false and `use_simple_model` is true. It combines the mock status, first log, metrics, and security values into a newline-separated response.

### ADK specialist agents

- **Log analysis**: `app/agents/log_agent.py` calls `analyze_logs` and writes `log_analysis`.
- **Infrastructure analysis**: `app/agents/infra_agent.py` calls `check_infra` and `check_kubernetes_status`, writing `infra_analysis`.
- **Security analysis**: `app/agents/security_agent.py` calls `scan_security`, writing `security_analysis`.
- **Root cause**: `app/agents/rootcause_agent.py` correlates the three output keys into `root_cause`.
- **Recommendations**: `app/agents/recommendation_agent.py` turns the root cause into prioritized remediation guidance under `recommendations`.
- **Report**: `app/agents/report_agent.py` formats a complete incident report.

### Workflow composition

- **Incident analysis**: `app/workflows/parallel_analysis.py` and `app/workflows/incident_workflow.py` implement parallel collection followed by sequential synthesis.
- **Remediation loop**: `app/workflows/remediation_loop.py` implements a maximum-three-iteration recommendation/report loop.

### Mock telemetry tools

- `app/tools/gcp_logs_tool.py` wraps the mock log service.
- `app/tools/monitoring_tool.py` wraps the mock metrics service.
- `app/tools/kubernetes_tool.py` returns a fixed `CrashLoopBackOff` and `OOMKilled` result.
- `app/tools/security_scan_tool.py` returns a fixed no-threat result with failed-login and suspicious-IP data.
- `app/tools/exit_loop_tool.py` defines a loop-exit helper, but it is not attached to the remediation workflow.

## 8. User Flow

1. An operator opens `/ui`.
2. The page displays defaults for user `rahul`, service `payment-service`, incident workflow, fast mode, and a sample payment-service question.
3. The operator submits the form.
4. Browser JavaScript posts the entered values to `/analyze`.
5. FastAPI validates the JSON body with Pydantic and rejects unsupported workflow names.
6. `run_agent` selects fast mode by default and gathers deterministic mock signals. If fast mode is disabled, it can use the local generator or ADK workflow according to the flags.
7. The API returns a success object containing workflow and user ID plus the selected result.
8. The browser renders either a formatted assistant response or a JSON-like simple view.

There is no implemented login, tenant selection, incident persistence, history retrieval, remediation approval, or infrastructure mutation flow.

## 9. Backend and APIs

### `GET /`

Returns:

```json
{
  "status": "CloudGuardian AI is running",
  "version": "1.0.0",
  "workflows": ["incident", "remediation"]
}
```

### `GET /ui`

Returns the static `app/ui/index.html` file. A 500 error is raised if the file is missing.

### `POST /analyze`

Request shape:

```json
{
  "user_id": "rahul",
  "workflow": "incident",
  "message": "Why is payment service failing?",
  "service_name": "payment-service",
  "fast_mode": true,
  "use_simple_model": false
}
```

`user_id`, `workflow`, and `message` are required strings. `service_name` is optional. `fast_mode` and `use_simple_model` are booleans.

For a dictionary result, the response has `status`, `workflow`, `user_id`, and the result fields. A typical fast response includes `mode`, `service`, `summary`, `signals`, and `recommended_next_steps`. For a text result, the text is returned in a `response` property.

### Incident and action API

- `GET /incidents`: lists in-memory incidents.
- `GET /incidents/{incident_id}`: returns one incident.
- `GET /pending_actions`: lists actions awaiting approval.
- `POST /actions/{action_id}/approve`: approves and executes a pending action in simulation mode.
- `POST /actions/{action_id}/reject`: rejects a pending action.

Approval requests use `{ "operator": "operator" }`. These endpoints are intentionally not an authentication system; the operator value is currently only an audit label.

### Internal business logic

`_guess_service_name` extracts a phrase ending in `service` from the message, or falls back to `target-service`. The fast and local paths call the mock services directly. The ADK path creates an `InMemorySessionService` session and consumes the final event emitted by `Runner.run_async`.

## 10. Database

No database is implemented.

- No schema, migrations, ORM models, repositories, or database connection code exists.
- Firestore is listed in `app/requirements.txt`, but no Firestore client is imported or used.
- Sessions use `google.adk.sessions.InMemorySessionService` and are lost when the process ends.
- No users, incidents, reports, telemetry snapshots, audit entries, remediation attempts, or history records are persisted.

## 11. Authentication and Security

No application authentication or authorization mechanism is implemented.

- `user_id` is an unverified request field, not an authenticated identity.
- No JWT, OAuth, session cookie, API-key validation, role checks, or tenant isolation exists.
- The README's Cloud Run command includes `--allow-unauthenticated`.
- FastAPI CORS, rate limiting, request-size controls, and audit logging are not configured.
- The security scan is a mock analysis and does not protect the API or perform a real security scan.
- The UI uses `innerHTML` for some response fields (`status`, `mode`, `service`, and `summary`), so live untrusted response values would require output encoding or DOM-safe rendering before production use.

The `.env` file contains a placeholder project ID and is excluded from Docker by `.dockerignore`. Real credentials are not present in the repository.

## 13. Known Issues or Limitations

1. **All telemetry is synthetic**: log, metric, Kubernetes, and security values are hard-coded. Results cannot describe real services.
2. **Fast mode masks ADK workflows by default**: `fast_mode=True` is the API default and takes precedence over `use_simple_model`.
3. **The simple output checkbox is frontend-only**: it is not included in the request body; it only changes how the browser renders the response.
4. **The local-model checkbox can appear ineffective**: when fast mode remains enabled, `use_simple_model` is never reached.
5. **Remediation is advisory only**: the loop does not apply or validate fixes, and `exit_loop_tool.py` is unused.
6. **No durable state exists**: sessions and all analysis state are process-local.
7. **No access control exists**: the API accepts arbitrary `user_id` values and the documented Cloud Run deployment is public.
8. **Live adapters are not present**: the current executor is simulation-safe and does not call Cloud Run, Kubernetes, or other infrastructure APIs.
9. **Vertex initialization is disconnected**: `app/config/vertex_config.py` initializes Vertex AI only if imported, but no normal entry point imports it.
10. **Dependency overstatement**: several declared Google Cloud and utility packages are not used by the current source.
11. **Limited automated tests**: the control-plane approval lifecycle is covered, but API contracts, ADK compatibility, live integrations, and deployment are not yet covered.
12. **Potential browser injection risk**: selected API response fields are interpolated into `innerHTML` in the UI.
13. **Tracked environment**: the repository tracks a large `venv/` directory. Although `.dockerignore` excludes it, a `.gitignore` and dependency-only repository workflow would be cleaner.
14. **External font dependency**: the UI requests Google Fonts at runtime and has no documented offline fallback beyond the generic family names.

No application `TODO`, `FIXME`, `NotImplemented`, or empty `pass` implementation was found in the application-owned source during this review. The placeholder `YOUR_PROJECT_ID` remains in `.env` and `README.md`.

## 15. How to Run the Project

The following steps are based on the current README and configuration files.

### Local setup

1. Use Python compatible with the project dependencies. The Dockerfile uses Python 3.11; the tracked local virtual environment contains Python 3.12 files.
2. From the repository root, install local fast-mode dependencies:

   ```powershell
   pip install -r app/requirements.txt
   ```

  For live ADK/Gemini analysis, use Python 3.11 and install the optional dependency set:

  ```powershell
  pip install -r app/requirements-ai.txt
  ```

3. Configure environment values. The current `.env` template is:

   ```text
   GOOGLE_GENAI_USE_VERTEXAI=TRUE
   GOOGLE_CLOUD_PROJECT=YOUR_PROJECT_ID
   GOOGLE_CLOUD_LOCATION=us-central1
   ```

   Replace `YOUR_PROJECT_ID` with a real Google Cloud project when using Vertex AI. Google Cloud credentials and permissions are not configured by this repository.

4. Start the local API from the repository root:

   ```powershell
   uvicorn app.main:app --reload
   ```

5. Open the documented Swagger UI at `http://127.0.0.1:8000/docs` or the operator console at `http://127.0.0.1:8000/ui`.

6. Run the focused control-plane tests:

  ```powershell
  pytest -q tests
  ```

7. Example request:

   ```http
   POST /analyze
   Content-Type: application/json

   {
     "user_id": "rahul",
     "workflow": "incident",
     "message": "Why is payment service failing?"
   }
   ```

  With omitted optional flags, this uses the deterministic fast path and creates an in-memory incident with pending action proposals.

### Docker and Cloud Build

The Dockerfile is intended to build and listen on port 8080:

```powershell
docker build -t cloudguardian-ai .
docker run --env-file .env -p 8080:8080 cloudguardian-ai
```

The repository's Cloud Build configuration can publish the image with:

```text
gcloud builds submit --config cloudbuild.yaml .
```

`cloudbuild.yaml` builds and publishes the image but does not deploy it. The README separately documents:

```text
gcloud run deploy cloudguardian-ai \
  --source . \
  --region us-central1 \
  --allow-unauthenticated \
  --set-env-vars GOOGLE_GENAI_USE_VERTEXAI=TRUE,GOOGLE_CLOUD_PROJECT=YOUR_PROJECT_ID,GOOGLE_CLOUD_LOCATION=us-central1
```

The Dockerfile now copies the package to `/app/app` and starts `app.main:app`, matching the source imports. The container instructions still require a real image build and runtime smoke test.

### Verification scope

The local fast-mode dependency installation completes on Python 3.14, and the focused control-plane tests pass. Live Google ADK installation and model invocation were not performed in this review.
